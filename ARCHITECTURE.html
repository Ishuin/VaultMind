System Architecture

VaultMind

Full-stack knowledge management platform with multimodal RAG pipeline, local AI inference, and BYOK architecture — designed to be rebuilt from scratch in any language

00 — What Is VaultMind?

💡 In Plain English

VaultMind is a personal knowledge base where you upload your documents (PDFs, Word files, text files) and then ask questions about them in natural language. Think of it like having a brilliant research assistant who has read every document you own and can instantly find, summarize, and connect information across all of them.

The analogy: Imagine a librarian who has memorized every book in your library. You ask "What did Dr. Smith say about climate change in the 2024 report?" and instantly gets the answer — pulling from page 47 of one PDF, a paragraph in a Word doc, and a note in a text file — all in under 2 seconds.

🔧 How It Works (No Jargon)

Step 1 — Upload: You drag-and-drop your files into the app. The system reads each file, breaks it into small chunks (like paragraphs), and converts each chunk into a mathematical fingerprint (called an "embedding") that captures its meaning.

Step 2 — Store: These mathematical fingerprints are stored in a special database called a vector database. Unlike a regular database that searches by exact keyword matches, a vector database can find chunks that are conceptually similar — even if they use different words.

Step 3 — Ask: When you ask a question, the system converts your question into the same mathematical fingerprint format, finds the most similar document chunks, and feeds them to an AI model along with your question. The AI then generates a clear, sourced answer.

The magic: You don't need to remember which document contains what information. You just ask, and VaultMind finds it.

02 — System Overview

Four-tier architecture: React frontend → FastAPI backend → dual storage (PostgreSQL + LanceDB) → local/cloud LLM inference

💡 In Plain English

VaultMind has four layers, like a sandwich: Layer 1 (the bread) is the website you see and interact with. Layer 2 (the filling) is the server that handles all the logic — processing files, running searches, talking to AI. Layer 3 (the other bread) is two databases — one for user accounts and metadata, one for storing the "mathematical fingerprints" of your documents. Layer 4 (the condiments) is the AI engine — either running locally on your machine (private) or via cloud APIs (flexible).

03 — RAG Pipeline

The complete flow from document upload to AI-generated answer — the core of VaultMind

💡 In Plain English

RAG stands for Retrieval-Augmented Generation. It's a fancy way of saying: "Before the AI answers your question, it first looks up relevant information from your documents." This prevents the AI from making things up (hallucinating) because it's grounded in your actual data.

📥

Ingestion Pipeline

7 Steps
01
Upload

Multipart form upload — PDF, DOCX, or TXT. File size limit: 50MB per file, 2000 docs per user.

02
Validate

Check file type, size, readability (85% printable chars), and user quota. Reject binary/scanned files with helpful errors.

03
Extract Text

pypdf for PDF, python-docx for Word, UTF-8 decode for TXT. Collapse 3+ newlines.

04
Chunk

RecursiveCharacterTextSplitter — 1000 chars, 100 overlap. Splits on paragraphs → lines → words → characters.

05
Embed

all-MiniLM-L6-v2 — 384-dimensional vectors, batched (64 chunks/batch) for bounded RAM.

06
Store in LanceDB

Bulk insert into document_chunks table. Auto-rebuild IVF_PQ index if >256 rows.

07
Record Metadata

Create row in PostgreSQL documents table. Background task — non-blocking HTTP response.

💬

Query Pipeline

6 Steps
08
User Query

Natural language question from chat interface. No special syntax required.

09
Embed Query

Same MiniLM-L6-v2 model encodes question into 384-dim search vector.

10
Vector Search

LanceDB IVF_PQ index — prefiltered by user_id, top-10 results, distance threshold < 1.5.

11
Build Context

Top chunks joined into context string. Truncated at 3000 tokens (~12K chars) to fit LLM window.

12
Optional Web Search

If toggle is on, DuckDuckGo fetches supplementary real-time results (5 results max).

13
Generate Answer

System prompt + context + user query → Ollama/NIM generates grounded answer with citations. Saved to conversation history.

06 — Scalability & Performance

Built-in optimizations for handling large document collections without adding new dependencies

💡 In Plain English

VaultMind is designed to handle tens of thousands of documents per user on a single machine. The key insight: instead of scanning every single document chunk every time you ask a question (which would be slow), we build a mathematical "index" — like the index at the back of a textbook — that lets the system jump directly to the most relevant chunks.

OptimizationWhat It DoesImpact
IVF_PQ Vector IndexAuto-created at 256+ chunks. Cosine metric, 16 sub-vectors. Rebuilt after bulk uploads.Sub-second search at 1M+ chunks (vs minutes with flat scan)
BTREE Index on user_idScalar index for filtered search. Avoids scanning all chunks when filtering by user.User isolation cost: O(1) instead of O(N)
Distance ThresholdChunks with cosine distance > 1.5 are filtered out. Prevents irrelevant context.Better answer quality, no wasted LLM tokens
Batched Embedding64 chunks per batch during encoding. Bounded RAM usage for large documents.100MB PDF: ~270MB peak RAM (vs unbounded)
Context Truncation3000 token budget (~12K chars). Low-relevance chunks dropped first.LLM never overwhelmed, consistent response quality
Background ProcessingDocument uploads processed via FastAPI BackgroundTasks. Non-blocking HTTP.Upload response in <100ms, processing happens async
File Size Limits50MB per file, 2000 docs per user. Validated synchronously before processing.Prevents memory exhaustion and abuse

📊 Performance Characteristics

Upload path: File read → text extraction → chunking (1000 chars/chunk) → batched embedding (64/batch) → LanceDB bulk insert. 100MB PDF processes in ~30-60 seconds. Response returned immediately via BackgroundTasks.

Query path: Embed query (10-50ms) → IVF_PQ vector search with user_id prefilter (<100ms) → distance threshold filtering → context truncation (3000 tokens) → LLM generation (1-10s). Total: 2-12 seconds end-to-end.

07 — Revenue Model

Founder-tier subscription system with sequential unlocking, 7-day free trial, and Razorpay payments

💡 In Plain English

VaultMind uses a founder pricing model: early adopters get the cheapest price forever. The first 50 people to sign up get "Founder 1" pricing ($19/month). When those 50 slots fill up, "Founder 2" unlocks at $49/month for the next 50. Then "Founder 3" at $149/month. After all founder slots are taken, new users pay standard pricing ($250/month). There's also a one-time Lifetime option ($999) that's always available.

10 — How to Rebuild VaultMind

Step-by-step guide for rebuilding this system from scratch in any language or framework

🔧 Blueprint for Rebuilding

If you're rebuilding VaultMind in a different language (Go, Rust, Java, Node.js, etc.), follow these steps:

1. Set up your database: You need PostgreSQL (or any relational DB) for users, documents, conversations, subscriptions. And a vector database (LanceDB, Pinecone, Weaviate, Qdrant, Milvus) for document chunks. The vector DB must support: 384-dimensional float vectors, cosine distance, filtered search by user_id, and ANN indexing.

2. Build the document pipeline: Accept file uploads → extract text (PDF via pdfplumber/pypdf, DOCX via mammoth/python-docx) → split into ~1000-character chunks with ~100-char overlap → generate 384-dim embeddings using any sentence-transformer model → store chunks + vectors in your vector DB.

3. Build the query pipeline: Accept user question → embed it with the same model → search vector DB for top-10 similar chunks (filtered by user_id, threshold < 1.5) → concatenate chunk texts (max ~12K chars) → send to LLM with system prompt + context + question.

4. Build the auth layer: JWT tokens (or any stateless auth). bcrypt password hashing. Per-user data isolation via user_id filtering on all queries.

5. Build the frontend: Chat interface, document upload, settings. Connect to your backend API. Store JWT in localStorage or cookies.

Key invariants: Every vector chunk must have a user_id. Every query must filter by user_id. The embedding model must be the same for indexing and querying. Chunk size should be ~250 tokens (~1000 chars). Context budget should be ~3000 tokens.
